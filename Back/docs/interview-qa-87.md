## 0. 开场

### 1. 用两分钟介绍这个项目

这是一个面向小团队的内部知识库平台，核心链路是「文档导入 → 权限控制 → AI 问答 → FAQ 沉淀」。

- **导入**：支持 Markdown / TXT / DOCX 本地解析，PDF / 旧版 Word 走 MinerU 云端解析；解析出的图片存 MinIO，并调用视觉模型生成图片说明。
- **知识**：一篇文档对应一个知识单元，正文按 800 字切分、100 字重叠，切片存 PostgreSQL，向量存 Milvus。
- **权限**：操作权限走 RBAC，数据权限独立建模，支持全局 / 部门 / 角色 / 用户四类授权；撤权立即生效，管理员也没有隐式数据权限。
- **问答**：关键词 + 向量混合召回，RRF 融合，鉴权后组装上下文，调用 DeepSeek 流式回答并返回引用；命中的原图会随回答展示。
- **沉淀**：问答日志定时挖掘成知识缺口和 FAQ 候选，人工审核后进入缓存。

技术上：FastAPI + Vue 3 + PostgreSQL 17 + Redis 7 + Milvus 2.5 + MinIO，本地 bge-m3 生成 1024 维向量，后台任务用数据库租约做可靠队列。

### 2. 为什么选 FastAPI + PostgreSQL + Milvus，而不是 Node/Java + pgvector

三个原因：

1. **团队能力与迭代速度**：FastAPI + Pydantic 的接口定义和校验成本最低，SQLAlchemy 2.0 的类型化 ORM 足够表达复杂授权查询。
2. **向量规模与检索质量**：pgvector 适合「业务数据和向量强一致、量级不大」的场景；本项目需要 HNSW、独立扩缩容和后续多模态扩展，Milvus 更合适。代价是多一套存储和一致性维护。
3. **已有基础设施**：目标服务器上已经跑着 PostgreSQL 17 和 Milvus 2.5，复用现有资源比引入新组件更现实。

取舍：pgvector 能省掉一套系统、让「撤权即失效」更简单（同一个事务）；Milvus 换来更好的召回性能和扩展性，但必须接受「向量是异步索引、可能短暂陈旧」的问题，并用版本校验兜底。

### 3. 重做一次会改哪三个决定

1. **导入流程不引入 LangGraph**：目前只有 4 个线性节点，图编排带来的抽象成本大于收益，直接写一个带检查点的函数更清楚。
2. **图片访问改成读取时动态签名**：现在是写入时生成的长期能力地址，撤权后仍可访问，不符合严格的权限语义。
3. **Worker 与 Web 进程早期就解耦**：现在默认随后端自动启动，开发方便，但多实例部署时必须改配置，容易踩坑；应默认独立部署。

## 1. 架构与分层

### 4. routers / services / repositories / models 的边界

- **routers**：只做 HTTP 适配——参数校验、依赖注入、权限入口、DTO 输出，不写业务分支。
- **services**：业务规则、事务编排、跨实体协作（如导入、问答、权限判定）。
- **repositories**：纯查询与持久化，不抛业务异常、不做鉴权。
- **models**：ORM 与约束，是数据一致性的最后一道防线（唯一约束、CHECK、外键）。

放错层的典型痛点：把鉴权写进 repository，会导致所有调用方共享隐式权限；把外部调用（MinerU、LLM）放进事务里，会长时间占锁。

### 5. Worker 两种模式（自动启动 / 独立运行）

- 默认 `WORKER_AUTO_START=true`：FastAPI 启动时用 `spawn` 子进程拉起 Worker，并由 `WorkerRuntime` 监控，异常退出自动重启；关闭后端时先请求停止，超时再 terminate/kill。
- 也保留 `python -m app.worker` 独立运行，用于生产扩容或多实例部署。

代价：自动模式开发和演示很方便，但多实例会重复消费任务（虽然有租约保护，仍浪费算力），且热重载会连带重启 Worker。生产建议 `WORKER_AUTO_START=false` + 独立 Worker 集群。

### 6. 用图编排导入流程的收益

`app/workflows/ingestion.py` 把导入拆成 `load_document → parse_document → analyze_images → persist_document`，每个节点只做一件事，条件边负责取消/提前结束。

收益：节点可单独测试、可观测（日志按节点输出）、取消检查点统一、后续加节点（如病毒扫描）不改主流程。对于更复杂的流程（分支、并行、重试策略）收益会更大；当前线性流程确实偏重。

### 7. 导入 State 为什么不入库，进程挂了怎么办

State 里只有任务 id、文件名、解析结果等**瞬时数据**，不放数据库连接、凭据或客户端。持久化边界是 `import_jobs`、`index_tasks` 和数据库事务，不是图状态。

进程挂掉后：任务租约过期，Worker 重新领取，从 `load_document` 重新执行，可能再次调用 MinerU；`persist_document` 之前会检查 `job.unit_id`，已经生成单元就不会重复创建。

### 8. 多实例部署会出问题的地方

1. **自动 Worker**：每个实例都起 Worker，重复消费（租约能防止重复写入，但浪费资源），必须关闭自动启动。
2. **本地模型**：每个 Worker 都加载一份 bge-m3，显存/内存成倍占用。
3. **登录限流**：用 Redis 计数，没问题；但如果 Redis 不可用，登录会整体 503（失败关闭）。
4. **SSE + 负载均衡**：需要关闭代理缓冲、保证长连接不被中断。
5. **定时挖掘**：`MiningService` 用了 PostgreSQL advisory lock，多实例安全，这点没问题。

## 2. 数据库与事务

### 9. 为什么用 UUID 主键

- 前端可先生成、跨表引用不需要回查自增 id；
- 导入、合并、迁移时不会冲突；
- 不暴露业务量级。

代价：索引更大、随机写入导致 B-tree 页分裂更严重。当前数据量小，收益大于成本；如果写入量很大，可以换 UUIDv7 或雪花 id 保持有序性。

### 10. current_version / acl_version / indexed_version / index_status

- `current_version`：正文版本，标题或正文变化时 +1；
- `acl_version`：授权变更次数，用于审计和缓存失效；
- `indexed_version`：最近一次成功写入 Milvus 的版本，检索时要求等于当前版本；
- `index_status`：`pending / ready / failed / deleted / canceled`，给前端和运维看。

缺任意一个都会出问题：没有 `indexed_version` 就无法判断向量是否陈旧；没有 `index_status` 前端无法区分「处理中」和「失败」。

### 11. knowledge_chunks 为什么带 version 和 ordinal

同一单元每次编辑都会生成新版本的切片，旧版本保留以便回滚和排查；`ordinal` 保证切片顺序和展示稳定。唯一约束是 `uq_chunk_position(unit_id, version, ordinal)`。检索时要求切片版本等于单元当前版本，避免旧向量命中。

### 12. 软删除还是物理删除

- 知识单元、会话用软删除（`deleted_at`）：可恢复、审计友好、引用关系不立即断裂。
- FAQ、缺口等管理数据用物理删除：数量可控，且删除时有缓存清理。

风险：所有查询都必须带 `deleted_at is null`。项目里在 repository/service 层统一加条件，测试覆盖了「删除后不可检索」。

### 13. knowledge_versions 存全量正文，数据量涨了怎么办

当前是「每次编辑存一份完整快照」，实现简单、回滚可靠。增长后的方案：

1. 只保留最近 N 个版本 + 定期归档到对象存储；
2. 改存差分（patch），但回放复杂；
3. 把版本正文移到单独的历史表/冷存储。

取舍：内部知识库文档更新频率低，全量快照的存储成本可以接受，优先保证可恢复性。

### 14. 一次「更新正文」动几张表，事务边界在哪

同时写：`knowledge_units`（版本 +1、正文）、`knowledge_versions`（新快照）、`knowledge_chunks`（新版本切片）、`index_tasks`（入队）、`faqs`（关联 FAQ 置为待审核、关缓存、revision+1）、`audit_events`。

事务边界是**一次 HTTP 请求一个数据库会话**（`app/core/dependencies.py` 请求结束时 commit）。向量写入在 Worker 里异步完成，属于最终一致，不放进这个事务。

### 15. 为什么 object_key 唯一，sha256 做什么

`object_key` 唯一防止同一对象被两条附件记录指向；`sha256` 用于完整性校验和未来的秒传/去重（当前只存储，未启用去重）。唯一约束也避免 MinIO 对象被误覆盖。

### 16. downgrade 抛异常、迁移直接执行整份 SQL 的风险

`downgrade()` 直接抛错，是为了防止误执行导致业务数据被删——这个系统的迁移只允许前进，回退必须人工备份后处理。

迁移里读取 `sql/001_schema.sql` 并整体执行，风险是：**迁移文件不是不可变的**，之后有人改了这个 SQL 文件，历史迁移的行为就变了，和生产库的实际结构产生漂移。正确做法是首次迁移后冻结该文件，后续变更一律新增 revision。

## 3. 权限模型

### 17. 操作权限和数据权限为什么分开

操作权限回答「你能做什么」（能否导入、审核 FAQ），由 RBAC 决定；数据权限回答「你能看哪条知识」，由 `unit_permissions` 决定。

分开的原因：同一个人可能有「知识管理员」角色，但只应看到自己部门的知识；把两者揉在一起会导致角色爆炸（每个部门一套角色）。

### 18. 四类授权如何做到四维 OR

`AccessRepository.condition()` 构造一个 EXISTS 子查询：

```sql
EXISTS (
  SELECT 1 FROM unit_permissions p
  WHERE p.unit_id = knowledge_units.id
    AND (p.target_type = 'global'
      OR (p.target_type = 'user'       AND p.target_id = :me)
      OR (p.target_type = 'department' AND p.target_id = :my_department)
      OR (p.target_type = 'role'       AND p.target_id IN (:my_roles)))
)
```

配合 `unit_permissions(unit_id)` 索引和 `uq_unit_target` 唯一约束，PostgreSQL 可以用 bitmap OR 合并。

**当前实现的边界**：部门授权是**精确匹配**，不会自动覆盖子部门。如果需要父部门授权向下继承，要用递归 CTE 展开部门树，或维护物化路径。

### 19. 为什么管理员没有隐式数据权限

`AccessService.allowed()` 只认显式授权，不做「超级管理员跳过」。好处是：

- 权限模型可验证，不会有隐藏后门；
- 审计上「谁能看什么」完全可解释；
- 避免管理员误操作导致敏感知识泄露。

代价：管理员需要给自己授权，初始体验不够顺滑。缓解方式是首次初始化时给管理员所在的部门授权，或在 UI 上提供「一键申请」入口。

### 20. 撤权后为什么立即生效，前端缓存怎么办

每次请求都会重新查数据库计算 ACL，不缓存权限结果，所以撤权后下一次请求就拒绝。

前端如果缓存了列表页，可能短暂显示旧标题。后端 `serialize()` 在无权限时把标题替换为「未授权知识单元」、正文清空，所以即使看到旧列表，点进去也拿不到内容；刷新或重新搜索即可恢复正确状态。

### 21. token_version 的作用

它是用户级的令牌代数，写进 JWT 的 `ver` 字段。改密码、停用账号、强制下线时 `token_version += 1`，所有旧令牌在校验时因 `ver` 不匹配立即失效。比维护令牌黑名单简单，也比纯 JWT 更可控。

### 22. JWT 无状态，为什么还要 auth_sessions

JWT 负责「令牌未过期且未被篡改」，`auth_sessions` 负责「这次登录是否仍然有效」：

- 登出时把对应 session 标记 `revoked`；
- 重置密码/停用账号时除了 `token_version`，也可以撤销全部会话；
- 记录 `expires_at`，支持服务端强制过期。

代价：每个请求多一次主键查询（可接受，且能命中缓存/连接池）。收益是登出和强制下线可以立即生效，这在权限敏感系统里是必需的。

### 23. 登录限流为什么失败关闭

`rate_limit` 走 Redis，Redis 不可用时抛 503，而不是跳过限流放行。理由是：登录是最容易被爆破的入口，限流失效时宁可暂时不可用，也不能放开。

可用性代价：Redis 故障会导致无法登录。缓解：Redis 做高可用、限流 key 带 TTL、监控告警；接受「安全优先于可用性」的取舍。

### 24. check-permissions 为什么要求 user_id

这是给**后端内部服务**调用的接口（例如 AI 服务校验一批单元的可读性），不是给页面直接用的。要求显式 `user_id` 是为了绑定被检查的主体：

- 查询自己的权限：拥有 `ai.access` 即可；
- 查询他人的权限：必须额外拥有 `knowledge.permissions`，且目标账号必须处于启用状态。

这样既支持内部服务代查，又不会变成「任意用户都能枚举他人权限」的接口。前端页面不直接调用它。

### 25. 历史回答为什么打码，在哪一层

`ChatService.message_dict()` 会逐条检查回答的 `source_versions`：只要有一个来源单元被删除、版本变化或当前用户失去权限，就把整条回答替换成「权限或版本已变更」，引用也清空。这一层在**读取历史**时做，而不是写入时，因为权限是动态变化的。

### 26. 大部门树、大量用户时，授权会慢在哪

当前实现每次请求要：

1. 查用户的角色列表；
2. 查 `unit_permissions` 的 EXISTS 条件；
3. 如果没有部门递归，成本主要是 `(unit_id, target_type, target_id)` 的索引扫描。

真正的风险在部门树扩展：如果要支持父部门继承，需要递归 CTE 或物化路径。优化手段：缓存「用户 → 可见单元集合」的版本号、给 `target_id` 加索引、把权限判定下推到 SQL 一次完成（当前已经是这样）。

## 4. 导入与并发

### 27. 为什么用 SELECT ... FOR UPDATE SKIP LOCKED

多个 Worker 同时抢任务时，`SKIP LOCKED` 让它们各自拿到不同的行，避免相互阻塞和重复消费。没有它，要么串行化严重，要么两个 Worker 抢到同一任务。

配合 `attempts`、`lease_generation`，构成一个基于数据库的可靠队列，不依赖 Redis 或消息中间件。

### 28. lease_until 和 lease_generation 各防什么

- `lease_until`：租约到期时间。Worker 定期续租；进程崩溃后租约过期，任务可被重新领取。
- `lease_generation`：每次领取 +1，写入时必须带上当前代次。旧 Worker 即使恢复，也因代次不匹配无法写回，避免「僵尸 Worker 覆盖新结果」。

续租失败时主动放弃，是因为无法确认自己仍持有任务，继续写会破坏一致性。

### 29. Worker 崩溃后多久恢复，会不会重复建单元

租约默认 1800 秒（可配），心跳每 30 秒续一次；崩溃后最多等租约过期即可重新领取。项目里还加了「等待 Worker 心跳」判断：没有 Worker 存活时，未领取任务 120 秒后直接判失败并提示，而不是无限等待。

不会重复建单元：`persist_document` 前检查 `job.unit_id`，已生成则直接结束；写入时又用代次校验，旧代次无法落库。

### 30. attempts 达到上限后怎么结束，导入和索引的差异

- 导入任务：达到上限后标记 `failed`，错误信息落 `job.error`，用户可以手动重试。
- 索引任务：达到上限后 `failed`，同时把单元的 `index_status` 置为 `failed`，并终止关联的导入任务（`terminal_index_failure`）。

索引任务失败会退避重试（30s × attempts），导入任务失败不自动重试，避免重复调用 MinerU 产生费用。

### 31. 取消导入时为什么要区分草稿

`cancel_import_index` 只丢弃「版本 1、草稿、没有任何授权」的知识单元。如果管理员已经编辑、发布或授权过，取消导入不能删除知识——否则会误删人工成果。此时只把任务标记取消，保留知识单元。

### 32. 取消后 MinIO 残留怎么办

原文件和已上传图片都会留在 MinIO，当前没有自动清理。这是已知缺口，合理方案是：

- 定期扫描 `attachments` 中未被任何单元引用、且创建超过 N 天的记录；
- 删除对象并清理数据库记录；
- 或者用对象存储生命周期规则按前缀过期。

### 33. 为什么要加「等待 Worker 心跳超时」

只看「任务创建了多久」会误判：Worker 可能正在处理另一个大文件，任务只是排队。心跳能区分「没人干活」和「有人在忙」。

规则：任务未被领取（`lease_until is null`、`attempts=0`）且超过 120 秒，并且 Redis 明确表示没有 Worker 心跳，才判失败；心跳未知（Redis 不可用）时宁可不判。

### 34. Worker 里调用外部服务时，事务是开着的吗

不是。`parse_import` 先开一个短事务读配置和检查取消，关闭后再调用 MinerU；`analyze_images` 同样在事务外调用视觉模型；`persist_document` 才是短事务。

这样避免网络调用期间持有行锁和连接，也避免长事务导致 vacuum 延迟。

### 35. 80 张图怎么控制耗时和费用，失败一张怎么办

当前实现：每份文档最多 100 张（`LLM_VISION_MAX_IMAGES`），逐张串行调用，单张超时 60 秒；任意一张失败会让整次导入失败并给出原因。

改进方向：

- 有界并发（例如 4 路），显著缩短总时长；
- 损坏/格式不支持的图片跳过并记录，不阻断整篇文档；
- 服务类错误（鉴权、限流）才终止并允许重试；
- 对小图（如 < 64px）或重复图片跳过分析。

## 5. 检索与 RAG

### 36. 从提问到返回引用的完整链路

1. 规范化问题，判断是否问候语；
2. FAQ 精确/语义匹配（命中且有权访问则直接返回）；
3. 关键词召回：切 2 字词，在切片正文和标题上 ILIKE，限已发布、未删除、当前版本；
4. 向量召回：bge-m3 编码问题，Milvus COSINE 搜 `top_k×4`，过滤低于阈值的结果；
5. 回 PostgreSQL 校验 chunk/unit/version，再按 ACL 过滤；
6. RRF 融合两路结果，取前 12，对话只用前 6；
7. 取出相关图片（最多 3 张）并转 base64；
8. 调用 DeepSeek 流式生成，SSE 推送 `session/citations/delta/usage/done`；
9. 写入聊天消息和问答审计日志；最后追加图片 Markdown。

### 37. 为什么按 2 字中文词切，有什么问题

中文没有空格，2 字 n-gram 能覆盖大多数双字词，实现简单、无需词典。问题：

- 「差旅报销」会被切成「差旅/旅报/报销」，包含噪声词；
- 英文和型号按非字切分，`HAK-180` 会变成 `hak` 和 `180`；
- 无法处理同义词和分词歧义。

更好的方案是 jieba 分词 + PostgreSQL pg_trgm/pg_jieba，或直接依赖向量召回，关键词只做兜底。

### 38. 为什么用 RRF 而不是分数相加

关键词得分是排名倒数（`1/(60+rank)`），向量得分是余弦相似度（0~1），两者尺度不同，直接相加会让某一路主导。RRF 只使用排名，天然对齐不同检索器，且对异常分数不敏感。

### 39. retrieval_min_score=0.35 怎么定的

这是一个偏召回的保守阈值：低于 0.35 基本是无关内容；但 bge-m3 对中文短文本的区分度有限，真实问题得分常在 0.54~0.66，问候语也能到 0.537，所以**单靠阈值无法区分相关与无关**。阈值只能挡掉明显不相关的，意图判断要单独做。

### 40. 向量命中后为什么还要回 PG 校验

Milvus 里的向量是异步写入的，可能落后于数据库：知识被编辑后旧版本向量还在，单元被删除或撤权后向量也可能残留。校验 `chunk_id` 存在、`unit_id` 一致、`version == current_version`、单元已发布未删除，才能保证返回的正文是当前且可见的。

### 41. degraded 标志为什么不能省

向量检索或模型不可用时，如果静默降级成关键词检索，用户会以为「知识库里没有这条」，从而产生错误的业务判断。`degraded` 让上层在「没召回到任何内容」时返回 503「向量检索暂不可用」，而不是「没有找到知识」。另外现在降级会打 warning 日志，避免 bug 被静默吞掉。

### 42. 「你好」为什么不能靠阈值过滤，最后怎么解决

实测「你好」的相似度 0.537，真实问题「hak180 怎么使用」也是 0.537，阈值无法区分。最终在 `ChatService.prepare` 里加了问候语白名单：去空格标点后精确匹配 `你好/谢谢/再见/在吗…`，命中则跳过检索、跳过 FAQ、直接返回引导语，并把审计结果记为 `smalltalk`，不生成知识缺口。

残留问题：非问候的无关问题（如「今天天气」）仍可能以 0.45 左右通过阈值。可选方案是「没有关键词命中且向量分 < 0.55 时不作答」，但会带来误杀风险，需要根据真实日志调参。

### 43. 切片 800 字、重叠 100 的依据

800 个中文字符大约 400~600 token，低于 bge-m3 的 1024 token 上限，留有余量；重叠 100 字保证跨段落的语义不被截断。切分优先在段落边界（`\n\n`）下刀，找不到才按硬长度切。

### 44. 纯图片切片为什么跳过

只有图片链接的切片没有可检索文字，把 URL 本身向量化会引入噪声，还会挤占 top_k 名额。跳过不影响展示，因为图片仍保留在 `knowledge_units.content` 里，详情页和回答附加图片都能渲染。

### 45. FAQ 命中缓存后为什么还要重新鉴权

FAQ 的答案来自知识单元，而权限和来源版本随时可能变化。`match()` 每次都调用 `readable()` 检查：来源单元存在、已发布、版本一致、当前用户有权访问。缓存 key 是 `faq:{id}:{revision}`，编辑答案、换来源、撤权都会让 revision 变化或直接失效，避免旧答案泄露。

### 46. 100 万切片时 HNSW 参数怎么调

当前 `M=16, efConstruction=200`，适合十万级。百万级建议：

- 提高 `M`（32）和 `efConstruction`（400），提升召回，代价是内存和构建时间；
- 查询 `ef` 随 top_k 增大（当前 `max(64, limit)`）；
- 按租户/部门分区或分集合，减少单集合规模；
- 监控 Recall 与 P99，必要时引入 rerank 模型。

### 47. [来源 3] 是模型编的还是约束的

引用列表由后端根据召回的切片生成（`plan['citations']`），不是模型输出。提示词要求模型标记来源，但即使它写出不存在的「[来源 9]」，前端也只展示后端给出的 citations，不会把模型文本当作可信引用。

## 6. 图片与多模态

### 48. MinerU 的 zip 里有什么，为什么只取一部分

zip 里通常有 `full.md`、`images/`、`content_list.json`（含每块的页码、坐标、类型）。当前只取 Markdown 和图片，丢弃 `content_list.json`，因此：

- 切片没有页码（`page` 为空）；
- 图片与图注的对应关系依赖 Markdown 的相邻位置；
- 无法做基于版面坐标的引用定位。

要继续提升，应解析 `content_list.json`，把 page_idx 和 bbox 映射到切片。

### 49. 图片为什么存 MinIO 而不是 base64 进库

- 数据库行会膨胀，备份、查询、迁移都变慢；
- 无法流式读取，前端要等整块数据；
- MinIO 支持大对象、生命周期和直接签名访问。

base64 只用在「发给视觉模型」这一步，属于传输编码，不落库。

### 50. 图片为什么用能力地址而不是登录鉴权

`<img src>` 由浏览器直接发起，无法携带 `Authorization` 头。因此用「附件 id + HMAC 签名」构成能力地址：不知道 id 或没有签名密钥就构造不出合法 URL，也不需要把登录态暴露给图片请求。

### 51. 撤权后图片仍可访问，怎么解释，怎么改

这是能力地址的固有限制：URL 本身就是凭证，签发给谁都能用，且写死在校验过签名的正文里。严格的做法是**读取时动态签名**：

- 正文里只存稳定的附件 id；
- 每次返回知识详情/回答时，按「当前用户 + 附件 id + 短期过期时间」生成 URL；
- 校验时同时验证签名和用户对所属单元的权限。

代价是需要在所有正文输出路径做改写，并处理缓存；这是下一步的安全加固项。

### 52. 为什么导入时分析图片，而不是回答时

导入时分析一次，结果进入正文和切片，图片就**可被文字检索**，成本只付一次；回答时再把原图发给模型，是补充视觉细节。两者分工不同：前者解决「找得到」，后者解决「看得清」。

### 53. 回答带图的成本怎么权衡

默认最多 3 张、单张 ≤5MB，只在 `LLM_VISION_ENABLED=true` 时生效，可通过 `LLM_ANSWER_MAX_IMAGES=0` 关闭。图片按 base64 计算 token，3 张图通常增加几百到一千 token，相比文本上下文可控；如果成本敏感，可以只对「问题包含看图类词汇」或「切片里只有图片」的情况附图。

### 54. GIF、超大图、伪造扩展名怎么处理

`prepare_image` 先用 Pillow 打开并 `verify()`，识别真实格式；像素数超过 4000 万直接拒绝（防解压炸弹）；尺寸超过 8192 或格式不在允许列表时，缩略并转成 PNG；伪造扩展名会在打开阶段失败并返回 400。GIF/WebP 支持，但动图只取首帧参与分析。

## 7. 接口与流式

### 55. 为什么用 POST + fetch 读 SSE，而不是 EventSource

EventSource 只支持 GET、不能自定义请求头，无法携带 `Authorization` 和提交长问题。项目用 `fetch` + `ReadableStream` 手动解析 SSE，既能 POST 带 body，又能通过 `AbortController` 中途取消。

### 56. 流式开始前为什么要 commit

在返回 `StreamingResponse` 之前先 `db.commit()`，把用户消息和会话落库。否则流开始后请求级会话可能被关闭，生成过程中再写库会失败，或者用户中断时连提问记录都没有。

### 57. 流到一半关页面或权限被撤，怎么感知

- 客户端断开会让生成器收到 `GeneratorExit`，`finally` 里把消息标记为 `interrupted=True` 并落库；
- 每批事件前调用 `still_allowed()` 重新检查用户状态、会话、权限和来源版本，失效立即抛 403 并停止；
- 响应头设置 `X-Accel-Buffering: no`，避免 Nginx 缓冲导致「看似卡住」。

### 58. 模型被截断时为什么判失败

`finish_reason=length` 说明回答不完整，保存半截答案会污染历史记录和后续上下文，也会让用户误以为结论完整。项目把它当作 502 错误，提示重试或调大输出上限；SSE 中断同理，不会标为成功。

### 59. 校验错误为什么只回字段名

Pydantic 的校验错误可能包含提交的值（例如密码、API Key）。统一异常处理只拼接字段路径（`loc`），不回显 `input`，避免把敏感信息写进响应和日志。

### 60. SafeMarkdown 为什么先禁 img 又放开

最初禁掉 `img` 是防 XSS 和外部追踪像素。支持文档图片后改为：允许 `img`，但用 DOMParser 过滤，只保留 `src` 以 `/api/knowledge/assets/` 开头的图片，其他一律移除，并加 `loading="lazy"`。这样既能显示自己的图片，又挡掉外链和注入。

## 8. 安全

### 61. 上传接口做了哪些校验

- 扩展名白名单：pdf/md/markdown/doc/docx/txt；
- 单文件 ≤50MB、单批 ≤30 个；
- PDF 校验 `%PDF-` 魔数；
- DOCX 校验是合法 zip，并限制解压条目数和总大小；
- 文件名和相对路径做路径穿越校验；
- 解析阶段再校验编码、二进制内容和文档结构。

只校验扩展名不够，所以加了魔数、zip 结构和解析阶段的深度校验。

### 62. DOCX 解压炸弹、超大 PDF、路径穿越在哪拦

- 路径穿越：`safe_upload_path()` 拒绝绝对路径、`..`、盘符和 NUL；
- DOCX：限制 ≤1000 个条目、解压后 ≤100MB；
- MinerU zip：≤20000 个条目、≤300MB；
- 图片：Pillow 像素上限 4000 万，捕获 `DecompressionBombWarning/Error`；
- 正文：解析后 ≤200 万字符。

### 63. API Key、数据库密码、MinIO 凭据存在哪

- 本地开发：`Back/.env`，已被 `.gitignore` 排除；
- 系统配置页写入的密钥：Fernet 加密后存 `integration_settings.secret_ciphertext`，密钥来自 `ENCRYPTION_KEY`；
- 前端永远不接触这些值，接口只返回 `hasApiKey` 之类的布尔值。

### 64. LLM_API_KEY 被系统环境变量覆盖的根因

pydantic-settings 的优先级是「进程环境变量 > .env」。桌面环境里另一个工具导出了全局 `LLM_API_KEY`，后端读到的是它的值，导致 DeepSeek 鉴权失败。修复是把字段的环境变量名改成带前缀的 `KB_LLM_API_KEY`（`validation_alias`），与其他工具的通用变量隔离。

### 65. 配置接口如何不回显密钥，密钥轮换怎么办

`IntegrationService.public()` 把 `api_key/password` 从返回值里 pop 掉，只给 `hasApiKey/hasPassword`。写入时如果没传密钥，会保留原密文，不会清空。

轮换 `ENCRYPTION_KEY` 会导致旧密文无法解密，接口明确返回 503「服务密钥无法解密，请恢复原 ENCRYPTION_KEY」。正确做法是支持双密钥解密一段时间、逐步重加密；当前版本没有做自动迁移。

### 66. 放到公网先改哪三件事

1. **TLS + 反向代理**：全站 HTTPS，关闭 `/docs` 和 OpenAPI（或加鉴权），设置安全响应头；
2. **网络隔离**：PostgreSQL/Redis/Milvus/MinIO 不暴露公网，改用私网或安全组，取消 SSH 隧道这种开发方式；
3. **暴力破解与滥用防护**：登录限流上移到网关、加验证码/锁定策略，上传和问答加用户级配额，审计异常访问。

另外还要：数据库最小权限账号、密钥托管（KMS/Vault）、备份与恢复演练。

## 9. 运维与部署

### 67. 为什么用 SSH 隧道

开发机在 Windows，数据库和 Milvus 只监听服务器内网/本机端口，没有公网暴露。SSH 隧道把远端端口映射到本地，既避免开放数据库端口，也复用现有 SSH 凭据。

生产不应依赖隧道：应用和中间件应部署在同一 VPC/私网，通过安全组限制来源。

### 68. 4GB 内存跑 Milvus 的风险

Milvus 官方建议至少 8GB。4GB 下的风险：

- 索引构建和数据加载时容易 OOM；
- 与 PostgreSQL、Redis、MinIO 抢内存；
- OOM Killer 可能杀掉容器，表现为随机不可用。

方案：扩到 8~16GB；或把 Milvus 拆到独立节点；降低单集合规模、控制并发；监控内存和容器 OOM 计数。

### 69. 三类数据怎么备份恢复

- **PostgreSQL**：`pg_dump` 逻辑备份或 `pg_basebackup` + WAL 归档做 PITR；
- **Redis**：AOF（已开启）为主，RDB 快照为辅，注意 AOF 与 maxmemory 策略；
- **Milvus**：备份 etcd 元数据 + MinIO 中的 segment 数据，或使用官方备份工具；恢复后需要重新 load；
- **MinIO**：原文件是权威数据，建议开启版本控制或跨节点复制。

关键是定期做**恢复演练**，而不只是备份成功。

### 70. Docker 旧代理导致拉镜像失败怎么绕过

服务器 Docker 配置了指向 `127.0.0.1:7890` 的代理，但该端口没有服务。临时方案：用服务器已有的 containerd 直接拉取官方镜像，导出成 tar，再 `docker load`。长期方案是删除或修正 `/etc/systemd/system/docker.service.d/http-proxy.conf` 并重启 Docker。

### 71. 时钟慢 11 小时，最先坏的是什么

最先坏的是 **MinIO 的 SigV4 签名**：请求时间与服务端相差超过 15 分钟会报 `RequestTimeTooSkewed`，所有上传下载失败。其次是 JWT 过期判断和日志时间。

容器共享宿主机内核时钟，修好宿主机后容器自动跟上，不需要重启；但已经建立的连接和定时器可能需要重连。

### 72. 日志在哪，怎么快速定位失败导入

目前日志输出到启动终端（stdout），没有集中收集。定位顺序：

1. 查 `import_jobs`：`status`、`phase`、`error`、`attempts`、`lease_until`；
2. 查 `index_tasks`：是否有失败、重试次数、错误；
3. 看 Worker 日志中对应任务 id 的节点输出；
4. 如果是 MinerU/LLM 问题，错误文本会明确写出（额度、Token、文件格式）。

改进方向：结构化日志 + request/task id + 集中存储（Loki/ELK）。

## 10. 性能与扩展

### 73. 平均耗时多少，主要花在哪

看板显示的累计平均约 24.5 秒，包含冷启动：首次请求加载 bge-m3 约 11 秒，MinerU 只在导入时有。单次问答稳定后大致是：

- 检索（编码 + Milvus）：几十毫秒到几百毫秒；
- DeepSeek 生成：1~5 秒（关闭思考模式后更快）；
- 图片 base64 传输：与图片大小相关。

测量方式：问答日志记录了 `response_time_ms`，按阶段再加细粒度计时会更准确。

### 74. CPU 和 GPU 差多少，为什么用 fp32

实测 bge-m3（1024 token 上限、batch 4）：

- CPU 约 0.28 秒/条；
- RTX 3060 约 0.02 秒/条，约 11 倍；
- fp32 显存占用 2.34GB，6GB 显卡有充足余量。

因此不需要 fp16；fp16 虽能省一半显存，但可能带来细微的向量精度损失，当前没有内存压力就不引入。

### 75. 50 个用户同时提问，瓶颈在哪

按可能性排序：

1. **Worker/导入**：单 Worker 串行处理任务，大 PDF 会阻塞后续导入；
2. **LLM 服务**：DeepSeek 的并发和速率限制，以及单次生成时长；
3. **数据库连接池**：当前 `pool_size=5, max_overflow=5`，高并发会排队；
4. **Milvus**：单机 4GB，查询并发高时内存和延迟都会吃紧。

问答本身是「检索 + 远程 LLM」，不占本地 GPU；本地 GPU 只用于切片向量化和问题编码。

### 76. top_k=12、对话只用 6 条怎么来的

12 是在召回率和上下文长度之间的折中：足够覆盖多篇相关文档，又不会让提示词过长。对话只用前 6 条，是为了控制 token、降低「无关片段干扰模型」的概率。数字可配，应该根据真实日志里的命中率和回答质量调整。

### 77. 知识量增长 100 倍先做什么

1. **缓存**：FAQ 缓存、热点问题缓存、Embedding 结果缓存；
2. **索引与查询**：确认所有 ACL 查询命中索引，减少 N+1；
3. **检索层**：Milvus 分区/分片、增加副本；
4. **重排**：先粗召回再 rerank，而不是无限加大 top_k；
5. 最后才考虑换向量库或上分布式。

## 11. 测试与工程质量

### 78. 72 个测试里最有价值的三类

1. **默认拒绝与撤权**：未授权看不到、撤权立即 403、历史回答打码；
2. **并发与失败**：Worker 重试、租约过期、取消导入、SSE 中断不算成功；
3. **输入安全**：路径穿越、zip 炸弹、旧版本向量、伪造来源。

这些覆盖的是「出错时会不会造成数据泄露或脏数据」，比 happy path 更有价值。

### 79. 为什么用内存假实现而不是起真实依赖

测试用 `tests/fakes.py` 替代 MinIO/Redis/Milvus/Embedder，换来：

- 秒级执行、无外部依赖、CI 可跑；
- 可精确构造失败场景（超时、异常）。

代价：测不到真实 API 契约问题。实际就漏过两个：Milvus 返回主键字段名是 `chunk_id` 而不是 `id`；系统环境变量覆盖 `.env`。所以还需要少量真实端到端测试兜底。

### 80. 哪些 bug 是测试没抓到、后来发现的

- Milvus 主键字段名假设错误，导致向量检索一直静默降级；
- 环境变量 `LLM_API_KEY` 覆盖 `.env`，导致 DeepSeek 401；
- `uv sync` 不带 extra 会卸载 torch/pytest；
- 导入后一直「处理中」缺少超时提示，后来加了 Worker 心跳判断。

共同点：都是「集成边界」的问题，单元测试用假实现时天然覆盖不到。

### 81. 端到端测试怎么写才不污染数据

这次的做法：

1. 在数据库里创建带随机后缀的临时管理员/普通用户；
2. 所有测试数据用固定前缀（`QA测试-`）；
3. 走真实 HTTP、真实 MinerU/DeepSeek，轮询任务状态；
4. 结束时按 id 和前缀删除单元、切片、向量、附件对象、会话、日志和临时用户；
5. 删除前先记录基线数量，结束后核对。

更严格的方案是独立测试库/独立 Milvus 集合，避免误删生产数据。

### 82. CI 会跑哪些步骤

顺序按「快 → 慢」：

1. `ruff check`（秒级）；
2. 后端 `pytest`（30~60 秒）；
3. 前端 `vue-tsc --noEmit` + `vitest`；
4. 前端 `vite build`；
5. Alembic 离线 SQL 生成校验（不连库）；
6. 可选：真实依赖的端到端测试（需要密钥和网络，放在 nightly）。

## 12. 反思类

### 83. 这个项目最脆弱的设计是什么

**能力地址（图片签名 URL）**。它把授权从「每次请求判定」变成了「一次签发、长期有效」，撤权后已泄露的 URL 仍然可读。对于权限敏感的知识库，这是语义上的缺口。

其次是单 Worker 串行处理导入与索引，一个慢任务会阻塞队列，且本地模型加载占用大。

### 84. 哪段代码当时想复杂了

导入流程用 LangGraph 编排。当前只有 4 个线性节点，用普通函数 + 显式检查点更易读；图的收益要等到出现并行分支、动态重试或人工审核节点时才明显。

另一个是 `acl_version`：目前主要用于审计和潜在缓存失效，实际读路径没有强依赖，字段价值偏低。

### 85. 如果要求「导入后立刻可搜到」

最小改动：导入完成时把 `status` 设为 `published`，并给一个默认授权（例如导入者所在部门）。

风险：

- 绕过人工审核，OCR 错误、敏感内容会立即进入问答；
- 默认授权范围可能过大，造成越权；
- 索引仍是异步的，「立刻」只能做到「发布后索引完成才可检索」。

更稳的方案：自动发布到「隔离区」，只有导入者可见，审核通过再扩大授权。

### 86. 撤权后图片必须立刻不可访问，怎么做

方案 A（推荐）：读取时动态签名。

- 正文只存附件 id；
- 每次输出正文时，按「当前用户 + 单元权限 + 5 分钟过期」生成 URL；
- 图片端点同时校验签名、过期时间和用户权限。

方案 B：图片端点走登录态（Cookie 或短期 token），由后端代理流式返回。

代价：需要改写所有正文输出路径、处理历史消息和缓存；高频访问时增加数据库鉴权开销。收益是权限语义完整，审计可通过。

### 87. 如何证明权限模型没有越权漏洞

从攻击面出发逐条验证：

1. **IDOR**：拿到别人的单元 id，直接 GET/PUT/DELETE，应 403/404；
2. **授权伪造**：普通用户调用授权接口、给自己加角色，应 403；
3. **撤权延迟**：授权后缓存/检索是否仍返回旧内容；
4. **历史泄露**：撤权后历史回答、FAQ 缓存、引用来源是否打码；
5. **向量陈旧**：编辑后旧版本向量是否还能命中；
6. **图片能力地址**：无签名、错误签名、他人附件 id 是否可读；
7. **会话越权**：删除/追加他人会话；
8. **登录面**：爆破、停用账号旧令牌、登出后重放；
9. **上传面**：路径穿越、zip 炸弹、伪造扩展名。

每一项都应有自动化测试；本次端到端测试覆盖了 1、2、3、4、8 的主要路径，向量陈旧和图片签名在单元测试里覆盖。
